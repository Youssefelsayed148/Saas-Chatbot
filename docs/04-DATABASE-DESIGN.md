## Constraints
Use UUIDs, FK constraints and explicit indexes `(tenant_id, bot_id)`; composite FKs where appropriate. Never accept tenant_id from public widget as authority; resolve through opaque bot locator. Full-text search columns are generated and GIN-indexed (docs/14 §5). Vector dimension is decided only if/when the semantic upgrade is approved. Index and publication design must ensure published-only retrieval. Password hashing via vetted library; no plaintext secrets in DB. Use Alembic migrations, not startup `create_all`.
## Transactions
Bot create + audit in one transaction; onboarding resource creation idempotent; job claim atomic; knowledge publication atomically swaps bot's published revision pointer; metering designed for retries and deduplication.

## Channel tables (P6, contract v1.1)
`channel_connections(id,tenant_id,bot_id,channel whatsapp|messenger|instagram,display_name,many_base_url,many_channel_ref NULL,status active|paused|revoked,ai_enabled,secret ciphertext + key version, previous secret + expiry,health_status,health_reason,health_detail,health_updated_at,last_event_at)` with a partial unique index on `(channel, many_channel_ref)` among non-revoked rows (0027). `channel_events(connection_id,event_id)` deduplicates inbound events. `conversations.connection_id` is a UUID FK (0023; playground thread keys live in `external_conversation_id`), `conversations.origin` JSONB holds the campaign. `messages.delivery_status` (`pending|sent|delivered|read|failed|unconfirmed`), `messages.error_code` (closed set), `messages.accepted_at` (0028, set when Many answers 202; the unconfirmed sweep uses it). Jobs: `channel_inbound`, `channel_send` (unique per message, `uq_channel_send_message`), `channel_health_poll` (one live job per connection, `uq_channel_health_poll_connection`). Migrations 0023-0030 (0030: partial index `ix_jobs_channel_health_poll_last` on `channel_health_poll` jobs).
