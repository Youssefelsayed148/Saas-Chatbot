## Foundation tables
`users(id UUID PK,email CITEXT UNIQUE,password_hash,verified_at,created_at)`; `tenants(id,name,slug UNIQUE,status,created_at)`; `memberships(tenant_id,user_id,role,status, UNIQUE(tenant_id,user_id))`; `bots(id,tenant_id,name,status,config_json,published_revision_id NULL,created_at,updated_at, UNIQUE(tenant_id,id))` — `config_json` holds assistant/business name, description, welcome message EN/AR, opening questions, default language, support email/phone, colour/position, handoff toggle, allowed domains (validated by a Pydantic schema); `invitations(id,tenant_id,email,role,token_hash,expires_at,accepted_at,revoked_at,created_by)`; `audit_events(id,tenant_id NULL,actor_user_id NULL,action,target_type,target_id,metadata_json,created_at)`.

## Constraints
Use UUIDs, FK constraints and explicit indexes `(tenant_id, bot_id)`; composite FKs where appropriate. Never accept tenant_id from public widget as authority; resolve through opaque bot locator. Full-text search columns are generated and GIN-indexed (docs/14 §5). Vector dimension is decided only if/when the semantic upgrade is approved. Index and publication design must ensure published-only retrieval. Password hashing via vetted library; no plaintext secrets in DB. Use Alembic migrations, not startup `create_all`.
## Transactions
Bot create + audit in one transaction; onboarding resource creation idempotent; job claim atomic; knowledge publication atomically swaps bot's published revision pointer; metering designed for retries and deduplication.
